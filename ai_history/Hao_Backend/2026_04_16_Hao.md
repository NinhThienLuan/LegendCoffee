# Báo cáo tích hợp VNPay - LegendCoffee (16/04/2026)
**Người thực hiện:** Hào (Hao)
**Mục tiêu:** Xây dựng tính năng thanh toán trực tuyến bảo mật thông qua cổng VNPay cho hệ thống vận hành doanh nghiệp LegendCoffee (Kiến trúc Java Spring Boot MVC). Đảm bảo tính nhất quán của dữ liệu giao dịch và cập nhật trạng thái đơn hàng thời gian thực.

---

## 1. Tóm tắt Flow Thanh Toán (Quy trình kinh doanh)

Quy trình thanh toán VNPay đã được xây dựng hoàn chỉnh với 4 bước chính, tuân thủ chặt chẽ tài liệu của VNPay để chống gian lận và đảm bảo tính nhất quán của dữ liệu:

1. **Khởi tạo (Client -> Server):** Người dùng yêu cầu thanh toán cho 1 đơn hàng (`orderId`). Server kiểm tra đơn hàng, tự động lấy số tiền gốc (phòng chống user sửa payload HTML), tạo 1 bản ghi `Payment` với trạng thái `PENDING` trong Database. Cuối cùng, sinh ra 1 đường link bảo mật của VNPay và `redirect` người dùng sang đó.
2. **Thanh toán (Tại VNPay Sandbox):** Người dùng nhập thẻ ATM test và xác nhận.
3. **Hiển thị giao diện (VNPay -> Trình duyệt -> Server):** VNPay chuyển hướng người dùng trở về địa chỉ `Return URL` (của hệ thống. Chức năng này chỉ làm nhiệm vụ kiểm tra sơ bộ và hiển thị HTML (Thymeleaf) MÀ KHÔNG cập nhật Database (Vì người dùng có thể tắt trình duyệt giữa chừng).
4. **Cập nhật Database ngầm (VNPay Server -> Server):** VNPay âm thầm gọi Server-to-Server vào địa chỉ `IPN URL` bằng phương thức GET. Đây là **Nguồn chân lý duy nhất (Source of Truth)**. Code sẽ kiểm tra chữ ký điện tử HMAC-512, xác thực số tiền gốc của DB so với số tiền VNPay báo thành công, chống trùng lặp dữ liệu (idempotency check), sau đó mới cập nhật trạng thái `SUCCESS` vào bảng `Payment` và `Order`.

## 2. Chi tiết các API Endpoint đã triển khai

Tất cả các API nằm trong file `PaymentController.java` của `LegendCoffee`.

### A. API Khởi tạo thanh toán
*   **Method | URL:** `POST /payment/vnpay/create?orderId={id}`
*   **Security:** Bắt buộc phải Login (Bảo mật qua Spring Security session cookie `JSESSIONID`).
*   **Request Params:** `orderId` (Long) - Mã đơn hàng.
*   **Response:** Trả về HTTP Status `302 Redirect` tới URL của máy chủ VNPay (Kèm theo một chuỗi ký tự SecureHash dài mã hóa thông tin đơn hàng).
*   **Xử lý Logic:** 
    * Lấy IP thực của request (Bằng `WebUtils`).
    * Fetch `Order` từ DB, lấy số tiền `totalAmount`.
    * Tạo `Payment` Object (status = PENDING, method = VNPAY).
    * Mã hóa dữ liệu bằng `VNPayHelper.hmacSHA512`.

### B. API Hứng kết quả giao diện (Return URL)
*   **Method | URL:** `GET /payment/vnpay/callback`
*   **Security:** Public (`permitAll`) - Vì VNPay điều hướng user về, không mang theo Token/Session của hệ thống API mình.
*   **Request Params:** Chứa các chuỗi bắt đầu bằng chữ `vnp_` do VNPay gắn thêm vào (VD: `vnp_Amount`, `vnp_TxnRef`, `vnp_ResponseCode`, `vnp_SecureHash`).
*   **Response:** Trả về giao diện HTML (`templates/payment/payment.html`).
*   **Xử lý Logic:** Nhận query params, băm lại nội dung bằng khoá Secret từ file `application.properties`, so sánh với `vnp_SecureHash` của VNPay gửi xem có bị sửa kết quả không. Sau đó nạp vào Object `PaymentReturnDTO` truyền cho màn hình để hiện thông báo. **Không đụng chạm vào cập nhật trạng thái đơn hàng trong DB ở bước này.**

### C. API Hứng kết quả ngầm (IPN URL - Quan trọng nhất)
*   **Method | URL:** `GET /payment/vnpay/ipn`
*   **Security:** Public (`permitAll`) - Vì server của VNPay gọi thẳng cho Server của mình, chẳng có tư cách gì để bắt nó login cả. (Thường dùng Ngrok để test).
*   **Response:** JSON theo chuẩn cứng của VNPay. DTO: `VNPayIpnResponseDTO`. Bắt buộc phải có chữ hoa: `{"RspCode": "00", "Message": "Confirm Success"}` (Jackson property annotation).
*   **Xử lý Logic:**
    1. Kiểm tra chữ ký hợp lệ không.
    2. Quét DB tìm Database `Payment` thông qua `vnp_TxnRef`.
    3. Idempotency Check (Kiểm tra xem Payment này đã từng xử lý `SUCCESS` hay chưa, vì mạng chập chờn VNPay có thể gửi kết quả 3-4 lần).
    4. Kiểm tra Validation mức độ 2: Số tiền thực tế thanh toán có khớp từng đồng với `amount` trong DB hay không.
    5. Update `Payment` và `Order` thành `SUCCESS` hoặc `FAILED` tuỳ thuộc vào mã `vnp_ResponseCode = 00`.

## 3. Các thành phần Code đã refactor và chia lớp

Đảm bảo nguyên tắc Clean Code và Single Responsibility:

1.  **Chuyển đổi cấu trúc Package (Migration):**
    * DTO request/response được gom gọn vào `dto/request` và `dto/response`.
    * Tách riêng `WebUtils.java` vào package `common/util/` thay vì viết dơ trong Controller, giúp ứng dụng có thể tái sử dụng dễ dàng hàm `getClientIp()` và `extractQueryParams()`.
    * VNPay logic mã hoá nằm riêng ở `common/util/VNPayHelper.java`. (Giữ phần Domain Payment độc lập).
2.  **Configurations:**
    * File cấu hình hệ thống nằm cứng ở `application.properties` với các biến environment để thay thế khi lên Cloud: `VNPAY_TMN_CODE`, `VNPAY_HASH_SECRET`.
    * Thêm `spring-boot-configuration-processor` vào `pom.xml` để cấu hình VNPay có thể binding tự động xuống Class thông qua `@ConfigurationProperties`.
    * Cập nhật file `SecurityConstants.java` whitelist `/payment/vnpay/callback`, `/payment/vnpay/ipn` bypass qua bước đăng nhập.
3.  **Entity và Database (Sử dụng H2 In-Memory tạm thời để test):** 
    * Khởi tạo file `DataInit.java`, tạo sẵn User (`admin`/`user`) và châm mồi 2 Order (Giá trị 150.000 và 300.000) vào DB mỗi khi hệ thống chạy để team Dev có dữ liệu rác tiến hành Postman / Web Testing liền ngay lập tức mà khỏi cần đi qua thao tác chọn giỏ hàng từ đầu.

## 4. Ghi chú khắc phục sự cố (Troubleshooting Log)

**Vấn đề 1: Lỗi 403 Forbidden khi Test API `POST /payment/vnpay/create?orderId=1` trên Postman.**
*   **Nguyên nhân:** Lỗi liên đới do Content-Type trong tab auth. Lớp Spring MVC Authentication mặc định cấu hình lấy thông tin qua Form gửi trên HTML (`application/x-www-form-urlencoded`). Team lại set body gửi đi là `multipart/form-data`, dẫn đến hệ thống không đọc được `email` và `password`, đồng nghĩa với việc Login thất bại. Request đi không có SessionID Cookie đính kèm, lập tức bị Firewall Spring Security đá ngược ra (nảy về trang web HTML Login tĩnh giao diện cũ).
*   **Khắc phục (Fix):** Hướng dẫn đổi Content-Type trong Postman, hoặc mở Chrome lên đăng nhập UI bình thường, sau đó test trigger payment bằng lệnh form GET/POST thẳng trên trình duyệt.

**Vấn đề 2: Lỗi khởi tạo Database liên quan đến Reserved Keywords của SQL.**
*   **Nguyên nhân:** Quá trình sinh cấu trúc bảng (Hibernate DDL Auto) bị từ chối do trùng lặp với các từ khóa mặc định (reserved keywords) của hệ quản trị cơ sở dữ liệu, cụ thể là các cột mang tên `value`, `type`.
*   **Khắc phục (Fix):** Đã sửa đổi trực tiếp cấu trúc bên trong các class Entity (Promotion/Voucher/Variant). Đổi tên cột từ `value`, `type` qua tên cụ thể hóa chức năng hơn: `promotion_value`, `promotion_type`, `voucher_value`. Khởi chạy ứng dụng thành công, Database đã tự động generate mà không gặp lỗi khởi tạo DDL.
